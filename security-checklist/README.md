# 보안 이슈 대응 점검표

사고 접수부터 조치 검증까지 기록하고, 사고마다 적용한 기준판을 보존하는 브라우저 도구입니다.
HTML·CSS·순수 JavaScript만 사용하며 빌드 단계와 서버 측 저장이 없습니다. 기록은 브라우저 로컬 저장소에 남습니다.

## 실행

### 방법 1. 파일 직접 열기

`index.html`을 브라우저로 엽니다. 설치할 것이 없습니다.

### 방법 2. 로컬 서버

```bash
python3 -m http.server 4173
```

브라우저에서 <http://localhost:4173/> 을 엽니다. `npm start`도 같은 명령을 실행합니다.

> 두 방법은 브라우저가 서로 다른 저장 공간으로 취급합니다. 한쪽에서 쓴 기록은 다른 쪽에서 보이지 않습니다.
> 옮기는 방법은 아래 [실행 방식 사이에서 기록 옮기기](#실행-방식-사이에서-기록-옮기기)를 보세요.

## 테스트

Node.js 18 이상과 Python 3이 필요합니다.

```bash
npm install
```

```bash
npx playwright install chromium
```

```bash
npm test
```

`npm test`는 로컬 서버(4173 포트)를 띄우고 Chromium으로 `tests/checklist.spec.js`를 실행합니다.
검증 범위: 사고 등록, 72시간 경계, 완료·해당 없음 필수값, 기준판 추가·변경·삭제 표시, 기존 사고의 기준판 유지,
새로고침 후 저장 유지, JSON 백업 왕복, schema 1 백업·로컬 저장 마이그레이션, 단계 순서 변경, `file://` 실행.

## 파일 목록

| 파일 | 책임 |
| --- | --- |
| `index.html` | 화면 구조와 스크립트 로드 순서 |
| `css/styles.css` | 스타일 |
| `js/data/initial-guide.js` | 초기 기준 데이터 (2025 전자금융기반시설 48개 항목) |
| `js/data/steps.js` | 대응 단계 정의 (고정 ID, 표시 순서) |
| `js/logic.js` | 업무 로직: KST 시각, 기한 판정, 완료 조건, 기준판 비교. DOM·저장소를 쓰지 않는 순수 함수 |
| `js/schema.js` | 저장 형식 버전, 마이그레이션, 검증 |
| `js/storage.js` | 로컬 저장소 읽기·쓰기, JSON 백업 직렬화 |
| `js/app.js` | 화면 렌더링과 이벤트 처리 |
| `tests/checklist.spec.js` | 브라우저 자동화 테스트 (Playwright) |
| `tests/fixtures/schema1-backup.json` | 단일 파일 버전에서 실제로 만든 schema 1 백업 |
| `playwright.config.js`, `package.json`, `package-lock.json` | 테스트 설정 (앱 실행에는 필요 없음) |

`file://`에서도 동작하도록 ES 모듈 대신 일반 `<script>`를 순서대로 불러오고, 전역은 `window.SecurityChecklist` 하나만 씁니다.
의존 방향은 `data → logic → schema → storage → app` 입니다.

## 동작 규칙

- **접수 시각**: PC 시간대와 무관하게 KST로 입력·표시합니다. 미래 시각은 등록할 수 없습니다.
- **패치 확인 기한**: 사고마다 접수 후 N시간(기본 72)입니다. `패치 이력 확인` 단계의 확인 일시가 기한 정각 이하면 "기한 내 확인", 넘으면 "기한 후 확인"입니다. 확인 전에는 현재 시각이 기한을 넘는 순간 "기한 초과"가 됩니다.
- **완료**: 결과, 증적 참조, 확인 일시가 모두 있어야 하며 확인 일시는 접수 시각부터 현재 시각 사이여야 합니다. **해당 없음**: 사유가 있어야 합니다.
- **기준판**: 사고는 등록할 때 고른 기준판의 ID를 저장합니다. 새 판을 등록해도 기존 사고의 기준판과 관련 항목 목록은 바뀌지 않습니다.
- **기준판 비교**: 같은 계열에서 그 판보다 먼저 등록된 판 중 가장 최근 판과 비교합니다(연도순이 아니라 등록순). 분류·항목명·위험도가 달라지면 "변경"입니다.

## 저장 형식과 마이그레이션

로컬 저장 키는 단일 파일 버전과 같은 `incident-checklist-ko-v1`입니다.

| schema | 대응 결과 저장 방식 |
| --- | --- |
| 1 (단일 파일 버전) | `case.rows = [결과, …]` — 단계 배열의 인덱스에 연결 |
| 2 (현재) | `case.results = { "단계ID": 결과, … }` — 고정 단계 ID에 연결 |

- schema 1 데이터는 로컬 저장을 읽을 때와 JSON 백업을 가져올 때 자동으로 schema 2로 올립니다. 내보내기는 항상 schema 2입니다.
- 로컬 저장을 올릴 때 원래 내용을 `incident-checklist-ko-v1.before-schema-2` 키에 남깁니다. 읽을 수 없는 내용은 `incident-checklist-ko-v1.unreadable` 키에 남기고 안내를 표시합니다.
- **schema 2로 올라간 뒤에는 예전 단일 파일 `security-checklist.html`이 그 기록을 읽지 못합니다.** 예전 파일로 돌아갈 일이 있으면 올리기 전에 예전 파일에서 JSON 백업을 받아 두세요.

### 단계를 바꿀 때

`js/data/steps.js`에서:

- **순서 변경**: 배열 순서만 바꾸면 됩니다. 저장된 결과는 ID로 연결되어 있어 마이그레이션이 필요 없습니다.
- **단계 추가**: 새 고유 `id`로 항목을 넣습니다. 기존 사고에서는 "대기"로 표시됩니다.
- **단계 삭제**: 항목을 지우면 화면에서 사라집니다. 저장된 결과는 지워지지 않고 백업에도 남습니다.
- **`id`는 바꾸지 마세요.** 꼭 바꿔야 하면 `js/schema.js`의 `CURRENT_SCHEMA`를 올리고 `MIGRATIONS`에 변환 함수를 추가하세요.
- `SCHEMA_1_STEP_IDS`(schema 1 시절의 순서)는 과거 백업을 해석하는 기준이므로 고치지 않습니다.
- 기한 판정에 쓰는 단계는 `PATCH_STEP_ID`로 지정합니다.

## 실행 방식 사이에서 기록 옮기기

브라우저 로컬 저장소는 주소(출처)별로 나뉩니다. 아래는 모두 서로 다른 저장 공간입니다.

- 파일 직접 열기 (`file://…`). 브라우저에 따라 파일 경로가 달라져도 따로 저장될 수 있습니다.
- `http://localhost:4173`, `http://127.0.0.1:4173`, 포트가 다른 주소
- 다른 브라우저, 다른 브라우저 프로필, 시크릿 창

기록이 보이지 않으면 지워진 것이 아니라 다른 저장 공간을 보고 있는 것입니다. 다음 순서로 옮깁니다.

1. **기록이 있는 쪽**을 예전과 같은 방식·같은 브라우저로 엽니다. (예: 예전에 쓰던 `security-checklist.html`을 그 자리에서 그대로 엽니다.)
2. `백업` 탭에서 **JSON 백업 다운로드**를 누릅니다. `security-checklist-YYYY-MM-DD.json`이 저장됩니다.
3. **옮겨 갈 쪽**을 엽니다. (예: `http://localhost:4173/`)
4. `백업` 탭에서 **JSON에서 복원**을 누르고 2의 파일을 고릅니다.
5. 확인 창에서 계속을 누릅니다. **옮겨 갈 쪽의 현재 기록은 백업 내용으로 통째로 교체되며 합쳐지지 않습니다.** 옮겨 갈 쪽에 이미 기록이 있으면 먼저 그쪽도 백업을 받아 두세요.
6. `사고 대응` 탭에서 사고 목록과 기한 표시를 확인합니다.

단일 파일 버전에서 받은 schema 1 백업도 4에서 그대로 가져올 수 있습니다.
옮긴 뒤에는 한쪽만 계속 사용하세요. 양쪽에 따로 기록하면 나중에 합칠 방법이 없습니다.
